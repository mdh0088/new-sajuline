# Product Brief: AI BI 어시스턴트 (admin-backend)

---

## 1. Executive Summary

### 1.1 제품 개요
**AI BI 어시스턴트**는 사이트 관리자가 자연어로 질문하면 **MariaDB, MSSQL 2005, GA4** 등 이기종 데이터베이스를 조회하여 실시간 인사이트를 제공하는 **LangGraph 기반 멀티 에이전트 대화형 BI 시스템**입니다.

### 1.2 핵심 가치 제안
| 측면 | 기존 방식 | AI BI 어시스턴트 |
|------|----------|-----------------|
| 데이터 접근 | SQL 직접 작성 필요 | 자연어 질문으로 즉시 답변 |
| 분석 범위 | 단일 DB 수동 분석 | 멀티 DB 자동 크로스 분석 |
| 인사이트 | 정적 보고서 대기 | 프로액티브 후속 분석 제안 |
| 응답 시간 | 수 시간 ~ 수 일 | 수 초 내 실시간 응답 |

### 1.3 주요 기능
- **대화형 BI**: "오늘 매출 얼마야?" → 즉시 답변
- **멀티 DB 통합**: MariaDB + MSSQL 2005 + GA4 크로스 조인 분석
- **프로액티브 인사이트**: 답변 후 후속 분석 자동 제안
- **보안 최우선**: 읽기 전용, SQL 검증, 민감정보 마스킹

## 2. Core Vision

### 2.1 해결하려는 문제 (Problem Statement)

#### 현재 상황의 고통점
1. **데이터 접근성 부재**: 관리자가 매출/상담 데이터를 확인하려면 개발팀에 요청하거나 직접 SQL을 작성해야 함
2. **이기종 DB 분절**: MariaDB(매출/유저)와 MSSQL(상담로그)가 분리되어 통합 분석 불가
3. **실시간성 결여**: 정적 보고서는 이미 과거 데이터, 즉각적 의사결정 지원 불가
4. **전문 지식 의존**: SQL/BI 도구 전문 지식 없이는 데이터 기반 의사결정 어려움
5. **마케팅 데이터 단절**: GA4 유입 데이터와 매출 데이터 연계 분석 불가

#### 비즈니스 영향
- 의사결정 지연으로 인한 매출 기회 손실
- 개발팀 리소스의 비효율적 사용 (반복적 데이터 요청 대응)
- 상담사 성과 관리의 어려움
- 마케팅 ROI 측정 불가

### 2.2 솔루션 (Proposed Solution)

#### 핵심 아키텍처: LangGraph 멀티 에이전트 시스템

```
┌─────────────────────────────────────────────────────────────────┐
│                    🎯 Supervisor (오케스트레이터)                │
│                    - 자연어 질문 분석                            │
│                    - 작업 분할 및 라우팅                         │
│                    - 결과 통합 및 인사이트 도출                   │
└─────────────────────────────────────────────────────────────────┘
                               │
               ┌───────────────┼───────────────┐
               ▼               ▼               ▼
        ┌──────────┐    ┌──────────┐    ┌──────────┐
        │ MariaDB  │    │  MSSQL   │    │   GA4    │
        │  Agent   │    │  Agent   │    │  Agent   │
        │ (Async)  │    │  (Sync)  │    │  (API)   │
        └──────────┘    └──────────┘    └──────────┘
              │               │               │
              │         ┌─────┴─────┐         │
              └─────────┤  pandas   ├─────────┘
                        │  merge()  │
                        └───────────┘
                               │
                               ▼
                    ┌──────────────────┐
                    │ Response + 후속  │
                    │ 분석 제안        │
                    └──────────────────┘
```

#### 기술적 해결 방안
| 문제 | 해결책 | 구현 방식 |
|------|--------|----------|
| 이기종 DB | 병렬 조회 + 메모리 조인 | `asyncio.gather()` + `pandas.merge()` |
| MSSQL 2005 호환 | 동기 래핑 | `run_in_executor()` + TDS 7.0/7.1 |
| 크로스 DB 조인 | 키 매핑 템플릿 | `counselor_code↔m_code`, `user_id↔u_id` |
| LLM 환각 방지 | 4중 방어 | Prompt→SQL검증→결과검증→사용자확인 |
| GA4 연동 | Data API | 무료 할당량 내 유입 분석 |

### 2.3 차별화 요소 (Differentiators)

#### 경쟁 우위
| 차별점 | 설명 | 고객 가치 |
|--------|------|----------|
| **레거시 DB 지원** | MSSQL 2005 (TDS 7.0/7.1) 완벽 호환 | 기존 시스템 교체 없이 도입 |
| **EUC-KR 처리** | 한글 인코딩 이슈 완전 해결 | 데이터 손실 없는 분석 |
| **크로스 DB 조인** | 이기종 DB 실시간 통합 분석 | 통합 인사이트 즉시 확보 |
| **프로액티브 AI** | 답변 후 후속 분석 자동 제안 | 분석 깊이 자연스럽게 확장 |
| **4중 보안** | SQL 검증 + DB 권한 + 결과 마스킹 + 확인 | 안전한 데이터 접근 |

#### GA4 통합의 차별화 가치
- **유입-매출 연계 분석**: "카카오 유입 유저 중 결제한 사람 몇 명?" 즉시 답변
- **마케팅 ROI 측정**: 채널별 전환율, ROAS 실시간 계산
- **퍼널 분석**: 방문→가입→결제 퍼널 드롭오프 분석
- **무료 API 활용**: GA4 Data API 무료 할당량으로 비용 부담 최소화

## 3. 단계별 로드맵

### Phase 1: MVP Core (2.5주)
- [ ] 환경 설정 + 의존성 추가
- [ ] LangGraph 기본 구조 구축
- [ ] SQL Validator (2중 방어)
- [ ] MariaDB Agent 구현
- [ ] 날짜 파싱 유틸리티
- [ ] 응답 포맷터 (텍스트 + 테이블)
- **범위**: MariaDB 단일 DB, 매출/결제/유저 질의
- **완료 기준**: "오늘/이번 달 매출", "결제 건수" 답변 + 보안 테스트 통과

### Phase 2: 멀티 DB (3주)
- [ ] tm60_chatlog 모델 추가
- [ ] MSSQL Agent 구현 (EUC-KR, TDS 7.0)
- [ ] Cross-DB Joiner (pandas)
- [ ] 오케스트레이터 Supervisor + 병렬 실행
- [ ] SSE 스트리밍 응답
- [ ] Redis Checkpointing (대화 맥락 유지)
- **완료 기준**: "김철수 상담사 매출과 상담시간 알려줘" 답변 가능

### Phase 3: UX 고도화 (4주)
- [ ] Schema-aware RAG
- [ ] 프로액티브 인사이트 제안
- [ ] SSE 스트리밍 응답
- **완료 기준**: "매출 떨어졌네" → "원인 분석할까요?" 자동 제안

### Phase 4: 확장 (4주+)
- [ ] GA4 Agent 추가
- [ ] 유입-매출 연계 분석
- [ ] 시각화 (차트 생성)
- **완료 기준**: "이번 달 유입 경로별 전환율" 답변 가능

## 5. 리스크 평가 및 완화 전략

### 5.1 리스크 매트릭스

| 리스크 | 영향도 | 발생확률 | 우선순위 | 완화 전략 |
|--------|--------|----------|----------|----------|
| LLM 환각으로 잘못된 SQL | 🔴 높음 | 중간 | **1순위** | 4중 방어 체계 |
| MSSQL 2005 호환성 | 🟠 중간 | 높음 | **2순위** | TDS 7.0/7.1 + 호환 쿼리 패턴 |
| 크로스 조인 성능 | 🟡 중간 | 중간 | **3순위** | 페이지네이션 + 인덱스 활용 |
| LLM API 비용 | 🟡 중간 | 높음 | **4순위** | 캐싱 + Multi-LLM 전략 |
| GA4 API 할당량 | 🟢 낮음 | 낮음 | **5순위** | 캐싱 + 배치 조회 |

### 5.2 주요 리스크 상세 완화 전략

#### 🔴 LLM 환각 방지 (4중 방어 체계)
```
Layer 1: Prompt Engineering
├── Few-shot 예시로 정확한 SQL 패턴 학습
├── Schema-aware RAG로 테이블/컬럼 정보 주입
└── 명확한 제약조건 프롬프트

Layer 2: SQL 검증
├── AST 파싱으로 SELECT만 허용
├── 화이트리스트 키워드 검증
├── 테이블/컬럼 존재 여부 검증
└── 위험 패턴 탐지 (UNION, 서브쿼리 등)

Layer 3: 결과 검증
├── 결과 row 수 임계값 체크
├── 이상치 탐지 (극단적 수치)
└── NULL/빈 결과 처리

Layer 4: 사용자 확인
├── 생성된 SQL 미리보기 (옵션)
├── 위험 쿼리 시 확인 요청
└── 실행 취소 옵션
```

#### 🟠 MSSQL 2005 호환성
| 제한사항 | 해결책 |
|----------|--------|
| TDS 프로토콜 | pymssql + TDS 7.0/7.1 명시 |
| OFFSET/FETCH 미지원 | TOP N 사용 |
| CTE(WITH) 미지원 | 서브쿼리로 대체 |
| 일부 윈도우 함수 | 자체 조인으로 구현 |
| EUC-KR 인코딩 | charset='euc-kr' 설정 |

#### 🟡 LLM API 비용 최적화 (Multi-LLM 전략)
```python
LLM_CONFIG = {
    "primary": "gpt-4-turbo",      # 복잡한 분석
    "fallback": "gpt-3.5-turbo",   # 단순 질의
    "budget": "gemini-1.5-flash",  # 비용 최적화
}

# 라우팅 로직
def select_llm(query_complexity: float) -> str:
    if query_complexity > 0.7:
        return "primary"
    elif query_complexity > 0.3:
        return "fallback"
    return "budget"
```
